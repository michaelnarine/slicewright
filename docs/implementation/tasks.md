### Owner's UI and viewing list (2026-11-24), with correct terms

The owner is keeping this list for when work resumes; more items will follow, so ask for the rest before starting. Their original wording is kept in quotes. The terms below are the ones to use in code, docs and future sessions. Vocabulary check done via the research broker (`~/.cache/research-broker/20261124-211320/chatgpt.md`, unverified against Bambu Studio's current UI) and the repo; code pointers are under `addon/slicewright/`.

**1. Source meshes hide the Preview.** Owner: "the original mesh is still visible which blocks viewing the sliced output". Term: *source-model visibility in Preview* (a "ghosted" or "translucent model overlay" is the descriptive name for the faint variant; Bambu Studio's exact label is unconfirmed). Wanted: while the mode switch is on **Preview**, hide the source objects (or draw them translucent), restore them on **Prepare**; ideally a Preview option "Show model: off / ghosted / on", default off. Never change the user's own object `hide_viewport` data permanently; use a viewport-only mechanism (the draw handler skipping them, `hide_set`/local state restored on exit, or a shading override) and make sure it recovers after crashes or file save. Where: `blender/mode.py`, `blender/preview/ui.py`, `blender/preview/handler.py`.

**2. Layer slider.** Owner: "the layer viewer should also be a scrubbable slider like in the Bambu slicer (for planar slicing)". Terms: Bambu Studio and OrcaSlicer Preview have a vertical **layer range slider** (two thumbs, lower and upper layer; "layer slider" for short) beside the viewport and a horizontal **move slider** (a.k.a. G-code move or tool-position slider) that scrubs the moves of the top layer, with the nozzle marker. The add-on already has the layer range and scrub position as properties (`blender/preview/props.py`: layer range, scrub position; `core/nav`). Wanted: a viewport-attached, draggable layer range slider (and move slider) like Bambu's. Blender's panel UI cannot embed a custom draggable widget, so this is a viewport overlay drawn with the `gpu` module with a modal operator for mouse handling (or, as a cheaper first step, a layer-range `IntProperty` slider in the Preview panel). For non-planar (ZAA, relief) layers "layer" is not one Z plane; a different scrubbing control is to be designed later.

**3. Washed-out path colours.** Owner: "the colors for the path types are very washed out and looks almost white". Term: **Line Type** (Bambu/Orca; ours calls it feature type or *role* view mode) colour scheme and its legend. Likely causes to check: sRGB vs linear confusion in the palette UBO (`core/preview_palette.py`, `blender/preview/renderer.py`, `blender/preview/shaders.py`: values converted twice, or Blender's "Filmic/AgX" view transform on the 3D viewport lifting them; the shaders carry a saturation value in `u_eye.w`), too much specular or lighting term, or the viewport's colour management (view transform Standard vs AgX). Fix by comparing against libvgcode's colours; check it in Standard and AgX; the GUI screenshot tool (`addon/tests/tools/run_ui_shots.py`) can verify.

**4. Segmented buttons for short enums.** Owner: "dropdowns with <= 3 options -> segmented options (like tubes vs lines); more than 3 stay dropdowns unless the options have a lot of text". Term: an **expanded enum** (`layout.prop(data, "prop", expand=True)`, shown as radio/segmented buttons); the add-on already does it for Preview quality, Bake kind and settings role. Rule: render an enum or choice setting as expanded when it has 3 or fewer items and the longest label is short (say, at most about 14 characters, tunable; they also need to fit the narrow sidebar width, so fall back to a dropdown when the sum of label widths is too large); otherwise a dropdown (`layout.prop`). Put the rule in one place in the settings drawing code (`blender/ui/settings.py`, `core/settings_layout.py`) and test it. Boolean settings stay checkboxes.

**5. Settings layout.** Owner: "settings are just listed out as a bunch of settings; better layout, less cluttered, sections, more web-like". Terms: use **sub-panels** (`bl_parent_id`, collapsible, `DEFAULT_CLOSED` for rarely used ones) for sections, **panel headers** (`draw_header`) for the section enable-checkbox or summary, `layout.box()` for **cards**, `layout.row(align=True)` for grouped controls, `use_property_split` with `use_property_decorate = False` for label-left/value-right rows, `layout.separator(factor=...)` and `layout.label` for headings. Blender's API has no CSS-like cards, grids or tabs beyond these (a tab row can be faked with an expanded enum). Orca's own tab and group structure is already in the engine's schema (`tab_layout`; `core/settings_layout.py`), so sections should follow Orca's pages and groups (Quality, Strength, Speed, Support, Others), with a search/filter box (`settings_role` already filters by Simple/Advanced/Expert), a "modified" indicator and a per-setting reset, and the screenshot tool for review. Also add short summary lines per section when collapsed. **Depends on item 7 (and vice versa):** the sidebar is a narrow column, which is much of the clutter; the Slicer workspace can give settings a wide area, so sections must adapt to the width they get (the segmented-button rule from item 4 should use available width, not only label count) and also work in the plain sidebar for anyone not using the workspace. Do the section layout first, then build the workspace around it. Related: the existing UI polish items (Preview legend truncation, "Slicewright object settings" title).

**6. Build plate mesh.** Owner: "add a non-interactable mesh for the build plate". Terms: Orca/Bambu call the visible plate geometry the **bed model** (STL) with a **bed texture** (image), separate from the **bed shape** (`printable_area`, the polygon that defines the printable region); "build plate mesh" is a fine generic name. The add-on currently draws the bed with a `POST_VIEW` draw handler (`blender/bed_draw.py`: polygon, grid, exclusion area, volume wireframe), which is already unselectable. Two routes: (a) draw a textured/shaded plate quad (or an extruded slab) in the same draw handler: nothing to select, nothing in the outliner, no file data, matches the "non-interactable" ask; or (b) a real mesh object with `hide_select = True`, `display_type`, excluded from slicing, Arrange and the plate collection; `hide_select` leaves it pickable by some tools and it appears in file data, so prefer (a). Wanted: a plate surface with a slight thickness or texture (optionally from the printer's `bed_model`/`bed_texture` if present: currently ignored by design), Z = 0 on its top, drawn behind objects, no depth fighting with the grid, respects the plate-centre origin change below.

**7. A "Slicer" workspace.** Owner: a "slicer" layout profile, like the "Modeling", "Rendering" and "Geometry Nodes" tabs along the top. Term: a **workspace** (`bpy.types.WorkspaceTool`/`bpy.data.workspaces`; the tabs are workspace tabs, each owning a screen layout of areas/editors, an object mode and tool settings). Not an "app template" (that replaces the whole startup file) and not a "theme". Wanted: one extra workspace named "Slicer" next to the others: large 3D viewport with the Slicer sidebar tab open (N panel) and the Prepare/Preview header, a compact outliner (plate collection), a Properties editor, and optionally a Spreadsheet or Info editor for slice issues and a timeline-less layout; created the first time the add-on is enabled or from a "Add Slicer workspace" button, never overwriting a user's own layout, and removable. How (unverified, check on Blender 5.1): `bpy.ops.workspace.append_activate(idname="Slicer", filepath=<bundled .blend>)` from a small `.blend` shipped in the extension that holds only the workspace (and its screen), or build it in code by duplicating a workspace (`bpy.ops.workspace.duplicate`) and rearranging areas (`bpy.ops.screen.area_split`, set `area.type`, `space.show_region_ui`); `bpy.data.workspaces` has no `new()`. Workspaces are stored in the .blend file and the user's startup file, so check what happens when a scene is opened without the add-on, and keep it out of `~/Library/Application Support/Blender` unless the owner chooses to save startup (never call `save_userpref` or write the startup file from the add-on). **Depends on item 5 (and vice versa):** the workspace's main value for settings is space: a wide Properties editor or a widened sidebar lets settings use label-left/value-right rows and a roomier, sectioned layout (the closest Blender gets to a web-style page); it does not provide cards, tabs or grids, so the section work in item 5 is still required. Build the section layout first, then the workspace around it. Open check on Blender 5.1: putting Slicewright settings in the Properties editor means registering a Properties-editor tab (`bl_space_type = 'PROPERTIES'` with a context), which must be verified; fallback is a wide 3D-view sidebar. Related: the mode switch (Prepare/Preview) in the header and item 1 (hiding source meshes while previewing).

### Hidden internal marking (copyright text, name, brand)

Added 2026-11-24 at the owner's request. Terms: an **embedded** or **internal watermark/marking** (some call it a hidden signature); the owner's wording "hidden geometry". Put the text inside the part, in an internal layer (default: layer 2, the layer directly above the first layer), instead of on the bottom face where it is easy to see and sand off. The text is vector outlines (a Blender text object converted to curves/polygons, with a font, size, position, rotation and a chosen Z layer or layer range, anchored to the object so it follows moves).

Two modes:
1. **Negative (void) mode.** The text is empty and the surrounding area prints, so the text reads as a shallow void in that layer. Because it sits inside the part, the void is covered by the layer above (bridged), so it is invisible from outside and shows only when the part is cut or X-rayed. Needs enough depth (at least one layer, the first-layer height or more) and a size/line-width limit so the nozzle can resolve it (stroke width at least about 1.5x the line width, tested on the printers). Can be done with plain Blender geometry (a boolean difference of the text solid from the object at that Z) with no engine work; check how the engine and Orca's slicing treat a thin enclosed void and the bridge above it.
2. **Toolpath-traced (contour) mode.** The layer prints as solid (rectilinear, or the chosen pattern) and the text is *drawn by the toolhead* as extrusion paths along the letter contours (outline walls, or a different infill angle/pattern inside the letter shapes), so everything looks solid but the text is encoded in the path. Example: the owner's name traced with filament along its contours while the rest of the layer prints in rectilinear. It uses no gaps, so it is almost invisible from outside; it shows as a different print pattern if the layer is inspected (cut, X-ray, translucent filament). Routes: (a) a modifier volume with a layer range (height range modifier) shaped like the text, with its own wall loops or solid infill pattern and angle: needs the engine's reserved `add_volume` (same blocker as the stress-infill idea); (b) add-on-side path editing that inserts the contour moves into that layer (same family as brick layers and arc overhangs; engine returns structured moves); (c) an Orca engine patch (heavy). Verify first what Orca does at a boundary between two regions with different solid patterns.

Options to settle: text, font, size, position on the XY plane, layer (default 2) and thickness, mode, pattern, stroke width, mirror/flip so it reads correctly from the bottom or from above, per object, stored with the object and exported in the job, and an "off" default. Not for hiding anything that could mislead or hurt someone: keep to authorship marks. Related: the plate-centre origin and `add_volume` work.

### Lattice and conical support types

Added 2026-11-24 at the owner's request. The terms "lattice support" and "conical support" are the owner's; they are not names of Orca v2.4.2 settings as far as I know, so **ask the owner what they have in mind (and for a reference or example) before building**. Do not guess.

What the engine offers today (Orca v2.4.2, passed through as settings): `support_type` normal(auto/manual) or tree(auto/manual); style `default`, `grid`, `snug`, `tree_slim`, `tree_strong`, `tree_hybrid`, `tree_organic`; base pattern `default`, `rectilinear`, `rectilinear-grid`, `honeycomb`, `lightning`, `hollow` (and interface patterns). Support painting (enforcers and blockers) exists in the add-on's paint tools.

Reference from the owner: <https://www.tomshardware.com/how-to/choose-3d-printing-supports> (page text did not load for a direct fetch; summary comes from a broker read, unverified). It describes five categories, none called lattice or conical: tree supports (branching, less material; Cura), breakaway supports (solid columns, single-extruder default), auto-generated supports with blockers (Cura), manual supports (user-placed; a Cura plugin offers cylindrical, tube, cube, abutment, freeform and custom shapes; Meshmixer and Lychee also), and dissolvable supports (PVA; needs a dual extruder). Useful takeaways: manual, user-placed support shapes are a gap here (we have painted enforcers and blockers only), and a "conical" support may be one of those placed shapes. Dissolvable supports map to a second filament as support material (AMS or the H2D), a separate item from shape.

Likely readings to check with the owner:
- **Lattice:** a support body made of an open lattice or truss (cross-braced columns, gyroid/diamond or "cross" patterns like Cura's support patterns), lighter than a solid grid and easier to remove. Could be a new support base pattern, or generated geometry.
- **Conical:** supports with cone-shaped tips or tapering columns (small contact point, wide base), as in tree/organic supports or resin-style cone supports; or a conical body that widens toward the build plate for stability.

Routes: (a) expose any matching style or pattern the engine already has and label it clearly (cheap); (b) generate the support as editable Blender geometry (cones, struts, lattices) that is added to the plate as support-role volumes (needs the engine's reserved `add_volume` or support-enforcer meshes; the stress-infill research found infill-only modifier volumes need `add_volume`); (c) patch Orca's support generator (an engine patch under `engine/patches/orca`; heavy, AGPL-side only). Also decide: automatic generation vs user-placed supports, interface layers and Z gap, removal tests, and a printed comparison against tree supports on the P2S and A1 mini. Related: arc overhangs, non-planar.

### Arc overhangs (supportless horizontal features)

Added 2026-11-24. Printing horizontal shelves and large overhangs without supports by laying concentric arcs anchored to the wall below. Reference (owner's link, not yet read in detail): <https://www.cnckitchen.com/blog/arc-overhangs-a-new-way-of-printing-without-supports>. Related community tool: Steven McCulloch's ArcOverhang G-code post-processor (from memory, unverified). Do not confuse with `enable_arc_fitting` (G2/G3 output), which is unrelated.

Status today: not supported. Orca v2.4.2 has supports, bridge settings (`bridge_flow`, `bridge_speed`, `thick_bridges`, `max_bridge_length`, `bridge_no_support`), overhang quality controls (`overhang_fan_speed`, `detect_overhang_wall`, `overhang_reverse`, `overhang_flow_ratio`) and `make_overhang_printable`, but no arc-overhang toolpaths, and the engine API has no hook for custom toolpaths.

Possible route: a path-editing step on the add-on side that replaces the engine's bridge and overhang moves for suitable regions with arc paths (the engine returns structured moves, so this can be done in Python before export), in the same family as brick layers and non-planar. Needs: read the article and its limits (shapes it works for, cooling, flow, speeds, arc radius and step-over, anchoring), detect eligible overhang regions from the slice (not from the mesh alone), write the new moves and keep export and preview consistent, and a small printed test on the P2S and A1 mini before building anything. Keep it off by default and per-object.

### LAN printer library and discovery

Added 2026-11-24 at the owner's request.

Keep a library of registered printers and let the user find printers on the current Wi-Fi/LAN, then send a G-code or `.gcode.3mf` print job to any of them over the LAN.

What exists today (M9): manual printer records in the add-on preferences (host, kind, secret in the macOS Keychain, TLS pin), Send panel with OctoPrint, Moonraker and Bambu LAN (FTPS and MQTT), connection test, start-print confirmation.

What this task adds:
- **Discovery:** an explicit "Find printers on this network" action (never automatic, never a background scan), gated by the same online-access permission as sending. Candidates to evaluate, each to be verified before building:
  - Bambu LAN: SSDP-like `NOTIFY` announcements on UDP 2021 with HTTP-style headers: `Location` (IP), `USN` (serial), `DevModel.bambu.com`, `DevName.bambu.com`, `DevConnect.bambu.com` (community notes; some sources mention UDP 1990; not a Bambu-published spec). Home Assistant's `ha-bambulab` auto-discovers via SSDP and also accepts serial, IP and access code manually, so keep a manual path. Needs a real printer to verify.
  - OctoPrint: its discovery plugin announces `_octoprint._tcp` and `_http._tcp` over mDNS (default web port 5000). Moonraker: optional Zeroconf (default HTTP port 7125); its exact service type is unverified. mDNS is UDP 5353; a user-supplied subnet probe limited to known ports is the fallback.
  - macOS: browsing Bonjour or using local UDP broadcast can trigger the Local Network permission prompt (System Settings > Privacy & Security > Local Network), attached to the app that runs it (Blender); discovery must handle the permission being denied, and broadcasts do not cross VLANs. Research: `BlenderSlicer-local/research/lan-and-brick/lan-discovery.md`.
  - Discovery only proposes a record; the user confirms it, enters the access code/API key, and trusts the certificate (existing TOFU pin flow). No secret is ever auto-filled or sent during discovery.
- **Library:** named printers with a model/preset pairing, last-seen address (IPs change; re-find by serial or hostname), status (online, idle, printing), and a per-printer default format and folder. Optional "send to several printers" with an explicit per-printer confirmation for start-print.
- **Status view:** online/offline and basic state in the Send panel and the Printers box, polled only on user action or while the panel is open, within the tick budget.
- **Constraints to keep:** Bambu LAN Developer Mode only (no cloud API, no key extraction, no client spoofing, never the Bambu networking plugin); no outbound traffic while the online gate is off; secrets stay in the keychain; nothing scans networks the user did not select.
- **Needs hardware to verify:** the owner's Bambu P2S and Bambu A1 mini (see below). Broker research (`research/lan-and-brick/bambu-lan-mode-p2s-a1mini.md`, community sources, unverified against firmware): enable Settings > LAN Only, then Developer Mode, on the printer screen; MQTT 8883 as `bblp` with the access code, topics `device/<serial>/report` and `/request`; FTPS 990; certificates are self-signed (keep TOFU pinning); Bambu's January 2025 authorization firmware may block third-party control unless Developer Mode is on; the P2S manual documents Developer Mode; a `.gcode.3mf` can upload but fail to start depending on model and firmware, so the hardware test must cover start-print on both printers.

### Non-planar slicing: order of work and purpose

Decided 2026-11-24. Printers: **Bambu P2S** and **Bambu A1 mini**. Research and Stage 0 results are in `BlenderSlicer-local/research/non-planar/`.

**Purpose (the owner's main use case):** avoid delamination and easy break planes that planar printing creates. Layers that intersect along Z, instead of every joint lying in one flat plane, make a break along a single plane less likely.

**Order:**
1. **Z contouring (ZAA) first.** The engine already has it (`zaa_*` keys, Expert-only). Work: make it usable and trustworthy (corrected tooltips are done), decide whether to promote the keys to Advanced, plumb per-object use (done via per-object overrides), print tests on the P2S and A1 mini, and check what it does for layer-joint strength rather than only surface quality. Stage 0 found it helps slopes of about 2 to 20 degrees and does nothing above that.
2. **Then multi-millimetre relief** (the Stage 1 warp, slice planar, un-warp prototype in Python). Needs toolhead and nozzle clearance measurements for each printer, to set the slope and collision limits.

**Brick layers (to evaluate alongside; they target the same delamination problem and work with planar slicing):**
- Idea: alternate perimeter paths at Z offsets of half a layer, so bead joints in neighbouring walls interlock instead of lining up. Source: <https://www.cnckitchen.com/blog/brick-layers-make-3d-prints-stronger> (full notes: `BlenderSlicer-local/research/lan-and-brick/brick-layers-article.md`).
- Article details (broker read of the article, dated 2024-02-18; checked): done in Simplify3D with four processes (one per perimeter, one for infill): two use a 100% initial layer height and two 150%, giving the half-layer offset. Four samples per condition, PLA and PETG, 0.25 mm layers, 4 perimeters, no infill, DIY test machine: regular PLA 944 N and PETG 950 N; brick PLA 1072 N (+14%); brick PETG +10% (the article gives only the percentage; about 1045 N is a calculation). Tests at 0.2 and 0.3 mm were inconsistent and probably not significant (the author blames old, wet filament and thinks it works best with taller layers). Brick PETG samples showed secondary cracks. Fracture surfaces were zig-zag or conical instead of flat. A 2025 study (secondary) found +4 to 5% for PLA, and flow of 105 to 110% helped both patterns. In the 2025 Orca retest, 100% flow staggered samples could be weaker (voids); raising flow helped.
- Drawbacks reported: sloped top surfaces under-extrude, first and last layers need special handling, overhangs and adaptive layer height are problematic, extra moves; it mainly affects walls, not infill.
- Implementations: GeekDetour BrickLayers (G-code post-processor for PrusaSlicer, Orca and Bambu Studio); an OrcaSlicer "Stagger Perimeters" feature branch and fork, not in mainline (official issue 7282 open). Needs G-code with varied Z, not special firmware. Not in Orca v2.4.2 as far as known (unverified).
- Open questions: could the engine produce it (it already emits per-move Z for ZAA, so a half-layer perimeter offset may fit the same path machinery); interaction with ZAA; whether it is worth building before the printed comparison. Plan a small printed test (same specimen set as the stress-infill test) before building.
